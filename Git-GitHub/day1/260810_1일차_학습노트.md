# Git과 GitHub — 학습 노트

---

## 1. Git / GitHub

### 1-1. Git &amp; GitHub를 사용해야 하는 이유

Git을 쓰지 않으면 보통 파일을 수정할 때마다 `final.py`, `final_v2.py`, `최종완성.py`처럼 파일 이름을 바꿔가며 새로 저장하는 방식을 쓰게 된다. 이 방식은 시간이 지날수록 파일 수가 계속 늘어나고, 어떤 파일이 어떤 순서로 만들어졌는지, 왜 바뀌었는지에 대한 기록이 전혀 남지 않는다는 한계가 있다.

Git은 파일을 복사해 여러 개로 늘리는 대신 항상 최종 상태의 파일 하나만 눈에 보이도록 유지하고, 그동안의 변경 내역은 커밋(Commit)이라는 단위로 내부에 기록해 둔다. 필요한 경우 특정 시점의 커밋으로 파일 상태를 되돌릴 수 있고, 각 커밋에는 누가 왜 변경했는지에 대한 기록도 함께 남는다. 버전 관리가 필요한 이유는 다음과 같이 정리된다.

- 코드의 변경 이력을 언제, 누가, 무엇을 바꿨는지 체계적으로 기록하기 위해
- 문제가 생겼을 때 어떤 변경 때문에 발생했는지 추적하기 위해
- 필요한 경우 이전 상태로 코드를 되돌리기 위해
- 여러 사람의 작업을 하나의 흐름으로 충돌 없이 관리(협업)하기 위해

GitHub이 필요한 이유도 같은 맥락이다. 구글 드라이브나 이메일로 파일을 공유하면 최종 상태의 코드만 전달되지만, GitHub에 코드를 올리면 그동안의 커밋 이력(누가 언제 무엇을 어떻게 바꿨는지) 전체가 함께 공유된다. 다른 사람이 그 기록을 그대로 받아 필요한 경우 과거 시점으로 롤백하거나, 예전 작업 내용을 확인하는 것까지 가능해진다.

### 1-2. Git과 GitHub의 차이


| 구분     | 정체    | 역할                                               |
| ------ | ----- | ------------------------------------------------ |
| Git    | 프로그램  | 버전 관리를 도와주는 핵심 엔진. 컴퓨터에 직접 설치해서 사용               |
| GitHub | 웹 서비스 | Git을 기반으로 코드를 공유하고 협업하는 기능을 제공. 인터넷에서 동작(설치 불필요) |


Git이 버전 관리를 담당하는 프로그램이라면, GitHub은 Git으로 관리하는 프로젝트를 인터넷에 올려 다른 컴퓨터에서 다시 내려받거나 다른 사람과 공유할 수 있게 해주는 클라우드 서비스에 가깝다 — 구글 드라이브와 비슷한 성격이다. GitHub은 마이크로소프트가 인수한 서비스로, 개발자 대부분이 이력서 첫 줄에 GitHub 주소를 적을 만큼 널리 쓰인다. GitLab이나 Bitbucket 같은 대안도 있지만 사용 목적이 비슷해, 점유율이 가장 높은 GitHub으로 먼저 배우면 다른 서비스로도 쉽게 옮겨갈 수 있다.

### 1-3. Repository

Git을 사용하려면 먼저 어떤 폴더를 관리 대상으로 지정해야 하는데, 이 단위를 **Repository(저장소)**라고 부른다. 컴퓨터 안의 모든 파일을 Git이 무분별하게 추적하면 개인정보 노출 같은 보안 위협이 될 수 있기 때문에, 반드시 특정 폴더를 지정해 그 안에서만 변경 이력을 관리하도록 만든다.


| 종류                        | 위치                        |
| ------------------------- | ------------------------- |
| 로컬 저장소(Local Repository)  | 내 컴퓨터 안에 있는 저장소           |
| 원격 저장소(Remote Repository) | GitHub 같은 웹 서비스 위에 있는 저장소 |


### 1-4. Commit

**Commit**은 변경 사항을 하나의 기록으로 저장하는 단위이자, 그 저장하는 행위 자체를 가리킨다. Git에서는 일반적으로 쓰는 "버전"이라는 용어 대신 Commit이라는 용어를 쓰며, 버전 1·버전 2가 곧 Commit 1·Commit 2라고 이해하면 된다. Git의 버전 관리는 자동으로 이뤄지지 않으며, 사용자가 명시적으로 Commit을 해야만 그 시점의 변경 사항이 기록으로 남는다.

### 1-5. Branch

**Branch**는 원본 코드에서 뻗어 나온 독립적인 작업 흐름이다. 발표 자료의 테마를 바꿔보고 싶을 때 원본을 바로 수정하는 대신 복사본을 만들어 실험하고, 마음에 들면 그 복사본을 원본으로 삼거나 마음에 안 들면 지워버리는 방식과 같은 원리다. 원본에 영향을 주지 않으면서 새로운 기능을 개발하거나 새 라이브러리를 테스트해 볼 때 브랜치를 사용한다. 브랜치를 만드는 순간 완전히 빈 상태에서 시작하는 것이 아니라, **그 시점의 코드가 그대로 복제**된 상태에서 독립적으로 진행된다는 점이 핵심이다.

## 2. git 기본 명령어

### 2-1. git config

Git을 사용하기 전에 내 정보(사용자 이름, 이메일)를 Git에 등록하는 명령어다.

```bash
git config --global user.name "내_유저네임"
git config --global user.email "내_이메일주소"
git config --global list   # 등록된 정보 확인
```

`--global` 옵션은 이 설정을 컴퓨터 전체에 적용하겠다는 의미다.

### 2-2. git init

현재 폴더를 로컬 저장소로 초기화하는 명령어다.

```bash
git init
```

실행하면 폴더 안에 `.git`이라는 숨김 폴더가 자동으로 생성되며, 이 폴더가 있어야 Git이 그 폴더를 저장소로 인식한다. `.git` 폴더를 삭제하면 Git 설정 자체가 사라진다. 기본 브랜치 이름은 보통 `main`으로 표시되며, 예전 버전의 Git에서는 `master`로 표시되기도 하는데 이 경우 `git branch -m master main` 명령으로 이름을 바꿀 수 있다.

### 2-3. git status

현재 저장소의 상태(어떤 파일이 어떤 단계에 있는지)를 보여주는 명령어다.

```bash
git status
```


| 표시                                      | 의미                                  |
| --------------------------------------- | ----------------------------------- |
| Untracked files                         | Git이 아직 추적하지 않는 새 파일                |
| Changes not staged for commit(Modified) | 기존에 추적 중인 파일이 수정됐지만 아직 add 되지 않은 상태 |
| Changes to be committed                 | add를 거쳐 커밋될 준비가 된 상태                |


Git을 사용하다가 지금 상태가 헷갈릴 때는 일단 `git status`부터 실행해 확인하는 것이 기본이다.

### 2-4. git add

Working Directory에 있는 파일을 Staging Area로 옮겨, 커밋할 대상으로 지정하는 명령어다.

```bash
git add 파일명
git add .   # 변경된 파일 전체를 한 번에 staging
```

여러 파일을 동시에 작업하더라도, 그중 커밋하고 싶은 파일만 골라 `git add`로 선택할 수 있다. 자동으로 커밋되는 기능은 없으며, 항상 사용자가 직접 add할 파일을 선택해야 한다.

### 2-5. git commit

Staging Area에 올라온 파일들을 실제로 Repository에 기록하는 명령어다.

```bash
git commit              # 커밋 메시지 작성 화면(Vim)이 열림
git commit -m "메시지"   # 메시지를 바로 지정해 한 줄로 커밋
```

`git commit`만 입력하면 커밋 메시지를 작성하는 텍스트 에디터(Vim)가 열린다. `i` 키로 입력 모드로 전환해 메시지를 작성하고, `Esc`로 입력 모드를 해제한 뒤 `:wq`를 입력해 저장 후 종료한다. 매번 이 과정을 거치기 번거로우면 `-m` 옵션으로 메시지를 바로 지정할 수 있다. 좋은 커밋 메시지는 `add login api`, `fixed password validation bug`처럼 무엇을 변경했는지 구체적으로 담아야 하며, 하나의 큰 작업을 여러 개의 작은 커밋으로 나눠 작업하는 것이 문제 발생 시 특정 커밋만 골라 수정하기 쉬워 권장된다.

### 2-6. git push

로컬 저장소의 커밋 내역을 GitHub 같은 원격 저장소로 업로드하는 명령어다.

```bash
git push origin main
```

push를 하려면 로컬 저장소가 "어디로 올려야 하는지"를 먼저 알고 있어야 하므로, 사전에 원격 저장소 주소를 등록하는 절차(`git remote add origin <저장소 주소>`)가 필요하다. 이미 원격 저장소가 등록된 상태에서 다시 등록을 시도하면 `remote origin already exists` 오류가, 저장소 주소에 오타가 있으면 `remote: Repository not found` 오류가 발생할 수 있다 — 이럴 때는 `git remote -v`로 현재 등록된 원격 저장소 주소를 확인해 원인을 진단한다.

### 2-7. git pull

> 이 명령어는 과정에서 실습으로 직접 다루지는 않았지만, `git push`와 짝을 이루는 기본 명령어라 함께 정리한다.

원격 저장소의 최신 변경 사항을 로컬 저장소로 가져와 반영하는 명령어다.

```bash
git pull origin main
```

`git push`가 로컬에서 원격으로 올리는 방향이라면, `git pull`은 그 반대로 원격에서 로컬로 내려받는 방향이다. 여러 명이 같은 원격 저장소를 함께 사용할 때, 다른 사람이 먼저 push한 변경 사항을 내 로컬 저장소에 반영하기 위해 사용한다. 내부적으로는 원격 저장소의 변경 사항을 가져오는 `git fetch`와, 그 내용을 현재 브랜치에 합치는 `git merge`가 결합된 동작이다.

## 3. Branch

### 3-1. git branch 명령어

```bash
git branch 브랜치이름      # 새 브랜치 생성
git branch                # 브랜치 목록 확인(별표 * 가 현재 위치)
git switch 브랜치이름      # 브랜치 이동
git branch -d 브랜치이름   # 브랜치 삭제
```

브랜치를 만든 직후에는 새 브랜치와 원본 브랜치의 코드가 완전히 동일하다 — 폴더를 통째로 복사한 뒤 이름만 바꾼 것과 같은 상태이며, 이는 정상이다. 이후 새 브랜치에서 파일을 추가·수정하고 커밋하면, 그 변경 사항은 해당 브랜치 위에만 존재한다. 삭제하려는 브랜치 위에서는 자기 자신을 지울 수 없으므로, 다른 브랜치(main 등)로 이동한 뒤 삭제해야 한다. 브랜치를 삭제하면 그 브랜치에서만 존재하던 커밋은 로그에서 완전히 사라지고 되돌릴 수 없다 — 이는 같은 선상에서 이전 커밋으로 돌아가는 롤백과는 다른 개념으로, 애초에 존재하지 않았던 것처럼 그 갈래 자체를 없애는 것이다.

### 3-2. 브랜치 관리(main, develop, feature, hotfix, release)

브랜치를 무분별하게 만들고 합치면 코드 상태가 혼란스러워지기 때문에, 실무에서는 팀 단위로 브랜치 관리 규칙을 미리 정한다. 구체적인 전략은 회사나 팀 규모, 작업 복잡도에 따라 달라지지만, 가장 일반적으로 쓰이는 방식은 다음과 같다.


| 브랜치          | 역할                                                                      |
| ------------ | ----------------------------------------------------------------------- |
| main         | 배포 가능한 안정적인 버전만 유지하는 브랜치                                                |
| develop(dev) | 실제 작업 대부분이 이루어지는 브랜치. 기능 개발 내용이 누적됐다가 검증되면 main으로 보냄                    |
| feature/기능명  | 개별 기능을 개발하는 브랜치(예: `feature/signup`, `feature/login`). 완료되면 develop에 합침 |
| hotfix/...   | 긴급한 버그 수정을 위한 브랜치                                                       |
| release/...  | 배포를 준비하며 마지막 점검(버전 번호 정리, 최종 버그 수정 등)을 진행하는 브랜치                         |


> release 브랜치는 이 과정에서 명시적으로 다루지 않았으나, main·develop·feature·hotfix와 함께 널리 쓰이는 브랜치 전략(Git Flow)의 구성 요소라 목차에 맞춰 보충했다. develop에서 배포 준비가 끝난 코드를 release 브랜치로 옮겨 마지막 점검을 마친 뒤 main과 develop 양쪽에 반영하는 방식으로 쓰인다.

여러 명이 develop 브랜치에 동시에 직접 작업하면 코드가 섞일 수 있기 때문에, 기능 단위로 feature 브랜치를 따로 만들어 작업한 뒤 완료되면 develop으로 합치는 흐름이 일반적이다. 혼자 개발할 때는 이렇게까지 복잡하게 나눌 필요는 없다.

### 3-3. Fast-forward

**Fast-forward**는 병합 대상 브랜치가 현재 브랜치의 분기 이후 상태이기만 할 때(그사이 현재 브랜치에 다른 변경이 없을 때) 일어나는 병합 방식이다. 새로운 커밋을 만들지 않고, 현재 브랜치의 커밋 포인터를 병합 대상 브랜치의 최신 커밋 위치로 그대로 이동시킨다.

```bash
git switch main
git merge feature-branch   # main이 분기 이후 변경되지 않았다면 Fast-forward
```

### 3-4. 3-way merge

**3-way Merge**는 두 브랜치가 각각 독립적으로 진행되어 서로 다른 커밋을 갖게 됐을 때 일어나는 병합 방식이다. 한쪽으로 포인터를 옮기는 것만으로는 두 브랜치의 변경 내용을 모두 담을 수 없기 때문에, 두 브랜치의 변경 내용을 모두 포함하는 **새로운 병합 커밋**을 자동으로 생성한다. 병합 커밋을 만들 때 커밋 메시지 작성 화면(Vim)이 자동으로 열리며, 기본 제공되는 메시지(`Merge branch '브랜치이름'`)를 그대로 사용해도 되고 직접 수정해도 된다.

### 3-5. Merge conflict

두 브랜치가 **같은 파일의 같은 부분**을 서로 다르게 수정했을 때는 Git이 어느 쪽이 맞는지 스스로 판단하지 않는다. 임의로 하나를 선택해 덮어써 버리면 사용자가 모르는 사이에 코드가 유실될 수 있기 때문이다. 이런 상황을 **Conflict(충돌)**라 하며, 최종 코드가 어떤 모습이어야 하는지는 병합을 시도하는 사람이 직접 결정해야 한다.

```bash
git merge 브랜치이름
# Auto-merging hello.py
# CONFLICT (content): Merge conflict in hello.py
```

충돌이 발생한 파일을 열면 다음과 같은 표시가 나타난다.

```
<<<<<<< HEAD
Hello A
=======
Hello B
>>>>>>> 브랜치이름
```

`=`를 기준으로 위쪽은 현재 브랜치의 코드, 아래쪽은 병합해오려는 브랜치의 코드다. 둘 중 하나를 선택하거나, 둘을 조합하거나, 아예 새로운 코드로 대체하는 것까지 모두 개발자의 선택이며 정해진 정답은 없다. 충돌을 해결한 뒤에는 일반적인 커밋 절차와 동일하게 마무리한다.

```bash
git add hello.py
git commit -m "merge conflict in hello.py"
```

이 커밋 역시 두 브랜치의 내용을 하나로 합치는 병합 커밋이라는 점에서, 근본적으로는 3-way Merge와 같은 구조다.

## 핵심 정리

- Git은 버전 관리를 담당하는 프로그램, GitHub은 Git 기반의 코드 공유·협업 웹 서비스다.
- Repository는 Git이 관리하는 폴더 단위, Commit은 변경 사항을 기록하는 단위이자 그 행위다.
- Branch는 분기 시점의 코드를 복제해 독립적으로 진행하는 작업 흐름이며, 지워도 원본에는 영향을 주지 않는다.
- 기본 명령어 흐름은 `git config`(초기 설정) → `git init`(저장소 생성) → `git status`(상태 확인) → `git add`(스테이징) → `git commit`(기록) → `git push`/`git pull`(원격 저장소와 동기화) 순서로 이어진다.
- 브랜치 관리는 보통 main·develop·feature·hotfix·release로 역할을 나누되, 구체적인 규칙은 팀마다 다르다.
- 브랜치 병합은 분기 이후 변경이 없으면 Fast-forward(포인터 이동), 양쪽 다 변경됐으면 3-way Merge(병합 커밋 생성)로 이뤄진다.
- 같은 파일의 같은 부분이 충돌하면 Git은 자동으로 결정하지 않으며, 충돌 마커를 직접 편집해 해결한 뒤 add·commit으로 마무리해야 한다.
