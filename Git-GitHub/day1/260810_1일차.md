# 파일 복사 대신 커밋으로: Git 버전 관리 첫걸음

## 들어가며: 웹 서비스 구조를 마무리하고 Git으로

2주 차 강의는 지난주에 다룬 SQLite 데이터베이스 실습을 다시 확인하고, 네트워크·IP 주소·포트 번호·DNS 개념을 복습하는 것으로 시작했다. 웹 서비스 기초와 구조에 대한 이해라는 첫 챕터를 마무리한 뒤, 오늘부터는 새로운 파트인 Git과 GitHub을 배운다. 강사는 Git과 GitHub이 프론트엔드 개발이든 백엔드 개발이든 AI 개발이든 두루 사용되는 기초 기술이라는 점을 강조했다. 1일차의 목표는 버전 관리라는 개념 자체를 이해하고, Git의 핵심 개념(Repository·Commit·Branch·HEAD)을 익힌 뒤, 로컬 환경에서 Git을 설치하고 커밋을 생성하는 기본 흐름을 실습으로 확인하는 것이다.

## 핵심 개념 정리

### 복습: IP 주소와 포트 번호, 그리고 DNS

본격적인 Git 학습에 앞서 지난주 내용을 다시 짚었다. IP 주소는 인터넷상에서 컴퓨터를 식별하는 주소이고, 포트 번호는 그 컴퓨터 안에서 실행 중인 특정 프로그램을 구분하는 번호다. HTTP는 80번, HTTPS는 443번처럼 프로토콜마다 자주 쓰이는 포트 번호가 관례적으로 정해져 있다. 192.168.0.0 대역은 공유기를 가리키고 127.0.0.1(localhost)은 자기 자신의 컴퓨터를 가리키는 특수 목적 IP로, 개발 중인 서버가 정상 동작하는지 스스로 요청을 보내 확인할 때 주로 사용된다. 사람이 기억하기 어려운 IP 주소 대신 naver.com 같은 도메인 이름을 쓸 수 있게 해주는 것이 DNS(Domain Name System)이며, 브라우저가 도메인 이름으로 요청을 받으면 내부적으로 DNS에 IP 주소를 조회한 뒤 그 주소로 통신한다는 점을 curl -v 명령으로 다시 확인했다.

### 버전 관리가 필요한 이유

버전 관리(Version Control)는 파일이나 코드의 변경 이력을 체계적으로 기록하고 관리하는 것을 의미한다. 코드는 완성된 상태로 한 번에 만들어지는 것이 아니라 기능을 추가하고 수정하며 계속 변화하는데, 이 과정에서 언제, 누가, 무엇을 바꿨는지 기록해 두면 문제가 생겼을 때 원인을 추적하거나 이전 상태로 되돌릴 수 있다. 여러 사람이 함께 작업할 때 각자의 변경 내용을 충돌 없이 하나의 흐름으로 통합하는 협업에도 버전 관리가 필수적으로 쓰인다.

기존에 많이 쓰던 방식은 문서를 수정할 때마다 final.py, final_v2.py, 최종완성.py처럼 파일 이름을 바꿔가며 새로 저장하는 방식이다. 이 방식은 시간이 지날수록 파일 수가 계속 늘어나고, 어떤 파일이 어떤 순서로 만들어졌는지, 왜 바뀌었는지에 대한 기록이 전혀 남지 않는다는 한계가 있다.

Git은 이 방식과 근본적으로 다르게 동작한다. 파일을 복사해 여러 개로 늘리는 대신 항상 최종 상태의 파일 하나만 눈에 보이도록 유지하고, 그동안의 변경 내역은 커밋(Commit)이라는 단위로 내부에 기록해 둔다. 필요한 경우 특정 시점의 커밋으로 파일 상태를 되돌릴 수 있고, 각 커밋에는 누가 왜 변경했는지에 대한 기록도 함께 남는다.

### Git과 GitHub의 차이

Git과 GitHub은 이름이 비슷하지만 서로 다른 기술이다.

| 구분 | 역할 |
|---|---|
| Git | 버전 관리를 도와주는 프로그램. 컴퓨터에 직접 설치해서 사용 |
| GitHub | Git을 기반으로 코드 공유와 협업 기능을 제공하는 웹 서비스 |

Git이 버전 관리를 담당하는 핵심 엔진이라면, GitHub은 그 결과물을 인터넷에 올려 다른 컴퓨터에서 다시 내려받거나 다른 사람과 공유할 수 있게 해주는 클라우드 서비스에 가깝다. GitHub은 마이크로소프트가 인수한 서비스로, 개발자 대부분이 이력서 첫 줄에 GitHub 주소를 적을 만큼 널리 쓰인다. GitLab이나 Bitbucket 같은 대안도 있지만 사용 목적이 비슷해, 점유율이 가장 높은 GitHub으로 먼저 배우면 다른 서비스로도 쉽게 옮겨갈 수 있다.

### Git의 핵심 개념: Repository, Commit, Branch, HEAD

Git을 사용하려면 먼저 어떤 폴더를 관리 대상으로 지정해야 하는데, 이 단위를 **Repository(저장소)**라고 부른다. 개인정보가 담긴 파일까지 Git이 무분별하게 추적하면 보안 위협이 될 수 있기 때문에, 반드시 특정 폴더를 지정해 그 안에서만 변경 이력을 관리하도록 만든다. 내 컴퓨터에 있는 저장소는 로컬 저장소, GitHub 같은 웹 서비스에 올라간 저장소는 원격 저장소라고 구분한다.

**Commit**은 변경 사항을 하나의 기록으로 저장하는 단위이자 그 행위 자체를 의미한다. 버전 하나가 커밋 하나에 대응된다고 생각하면 된다.

**Branch**는 원본 코드에서 뻗어 나온 독립적인 작업 공간이다. 발표 자료의 테마를 바꿔보고 싶을 때 원본을 바로 수정하는 대신 복사본을 만들어 실험하고, 마음에 들면 그 복사본을 원본으로 삼거나 마음에 안 들면 지워버리는 방식과 같은 원리다. 원본에 영향을 주지 않으면서 새로운 기능을 개발하거나 새 라이브러리를 테스트해 볼 때 브랜치를 사용한다.

**HEAD**는 현재 내 코드가 어떤 커밋을 기준으로 하고 있는지를 가리키는 포인터다. HEAD가 최신 커밋을 가리키고 있으면 최신 상태의 코드가 보이고, HEAD를 과거의 커밋으로 옮기면 그 시점의 코드 상태로 돌아간다.

### 코드의 세 가지 상태: Working Directory, Staging Area, Repository

Git으로 관리되는 코드는 세 단계의 상태를 거친다.

| 상태 | 의미 |
|---|---|
| Working Directory | 파일을 실제로 수정하는 작업 공간. 기본 상태 |
| Staging Area | 커밋 대상으로 선택된 파일들이 모이는 대기 공간 |
| Repository | 커밋을 통해 실제로 기록이 반영되는 저장소 |

Git의 버전 관리는 자동으로 이루어지지 않는다. Working Directory에서 아무리 파일을 수정해도 그 내용이 바로 기록으로 남지 않으며, git add 명령으로 원하는 파일만 Staging Area로 올린 뒤, git commit 명령으로 그 파일들만 Repository에 반영해야 비로소 버전으로 기록된다. 이 구조 덕분에 여러 파일을 동시에 작업하더라도 그중 커밋하고 싶은 파일만 골라서 기록할 수 있다.

## 실습 과정

### Git 설치와 초기 설정

Mac에서는 패키지 관리자 brew로 `brew install git` 명령을 실행해 Git을 설치했고, Windows에서는 Git for Windows 설치 파일을 내려받아 설치했다. 설치가 끝나면 `git --version` 명령으로 버전이 출력되는지 확인한다.

Git을 사용하려면 먼저 GitHub 계정을 만들고, 그 정보를 Git에 등록해야 한다.

```bash
git config --global user.name "내_유저네임"
git config --global user.email "내_이메일주소"
git config --global list
```

`--global` 옵션은 이 설정을 컴퓨터 전체에 적용하겠다는 의미다. 등록 후 `git config list`로 정상 등록됐는지 확인한다.

### 로컬 저장소 만들기와 상태 확인

작업할 폴더를 만들고 그 폴더를 로컬 저장소로 지정하는 과정을 실습했다.

```bash
mkdir git
cd git
git init
```

`git init`을 실행하면 해당 폴더 안에 `.git`이라는 숨김 폴더가 자동으로 생성되며, 이 폴더가 있어야 Git이 그 폴더를 저장소로 인식한다. `.git` 폴더를 삭제하면 Git 설정 자체가 사라진다. 기본 브랜치 이름은 보통 main으로 표시되며, 예전 버전의 Git에서는 master로 표시되기도 하는데 이 경우 `git branch -m master main` 명령으로 이름을 바꿀 수 있다.

`git status` 명령으로 현재 저장소의 상태를 확인할 수 있다. 초기화 직후에는 "On branch main, No commits yet, nothing to commit" 세 줄이 출력된다.

### 커밋 생성하기

VS Code에서 hello.py 파일을 만들고 `print("hello")`를 작성한 뒤, 이 변경 사항을 커밋으로 기록하는 과정을 실습했다.

```bash
git status          # Untracked files: hello.py
git add hello.py     # Staging Area로 이동
git status          # Changes to be committed: hello.py
git commit           # 커밋 메시지 작성 화면으로 전환
```

`git commit`만 입력하면 커밋 메시지를 작성하는 텍스트 에디터(Vim)가 열린다. `i` 키를 눌러 입력 모드로 전환한 뒤 메시지를 작성하고, `Esc`로 입력 모드를 해제한 다음 `:wq`를 입력해 저장 후 종료한다. 매번 이 과정을 거치기 번거로운 경우 `git commit -m "메시지"`처럼 `-m` 옵션으로 메시지를 바로 지정할 수 있다.

### 여러 파일을 선택적으로 커밋하기

world.py 파일을 새로 만들고 hello.py도 함께 수정한 뒤, world.py만 커밋에 포함시키는 실습을 진행했다.

```bash
git add world.py
git commit -m "create world.py"
git status  # hello.py는 여전히 not staged 상태로 남음
```

이 실습으로 Staging Area에 올라간 파일만 실제 커밋에 반영된다는 점을 확인했다. 아직 완성되지 않은 hello.py의 변경 사항은 커밋하지 않고 Working Directory 상태로 남겨둘 수 있다.

### git restore로 작업 내용 되돌리기

hello.py에 느낌표 세 개를 추가한 뒤, 이 변경을 취소하고 싶을 때는 `git restore .` 명령을 사용한다. 이 명령은 마지막 커밋을 기준으로 현재 코드 상태를 강제로 맞춰주며, 여러 파일을 동시에 수정한 상태에서도 한 번에 모든 변경 사항을 되돌릴 수 있다는 점에서 각 파일을 일일이 되돌리는 것보다 효율적이다.

### git log와 HEAD 이동

`git log` 명령으로 지금까지 생성한 커밋 목록을 확인했다. 커밋은 오래된 순서부터 아래에서 위로 쌓이며, 각 커밋마다 커밋 해시라는 고유 ID 값이 발급된다. HEAD는 이 중 가장 최근 커밋을 가리키고 있다.

```bash
git switch --detach 05c8503   # 첫 번째 커밋으로 HEAD 이동
git switch main               # 다시 최신 상태(main)로 복귀
```

`git switch --detach`에 커밋 해시를 지정하면 HEAD가 해당 커밋으로 이동하며, 그 시점 이후에 만들어진 파일(world.py)은 화면에서 사라진다. 다시 `git switch main`을 실행하면 최신 상태로 복귀하면서 사라졌던 파일이 다시 나타난다. 이 과정을 통해 HEAD가 실제로 코드의 현재 상태를 결정하는 포인터라는 점을 눈으로 확인했다.

### 좋은 커밋 메시지 작성법과 .gitignore

커밋이 수백, 수천 개로 늘어나면 메시지만으로 각 커밋이 어떤 작업이었는지 파악해야 하므로, 메시지는 무엇을 변경했는지 구체적으로 작성해야 한다. `add login api`, `fixed password validation bug`, `refactor user service`처럼 어떤 작업을 했는지 한눈에 알 수 있게 쓰는 것이 좋은 예시로 제시됐다. 하나의 큰 작업을 여러 개의 작은 커밋으로 나눠서 작업하는 것도 권장되는데, 이렇게 하면 특정 부분에 문제가 생겼을 때 해당 커밋만 골라 수정하기가 쉬워진다.

API 키 같은 민감한 정보를 담은 `.env` 파일이 실수로 커밋되어 GitHub 같은 공개 저장소에 올라가면, 크롤링을 통해 짧은 시간 안에 키 값이 탈취될 수 있다는 위험이 설명됐다. 이를 방지하기 위해 `.gitignore` 파일을 만들어 Git이 특정 파일을 아예 추적하지 않도록 지정한다.

```bash
# .gitignore 파일 내용
.env
```

`.gitignore` 파일을 만든 뒤에는 `git status`를 실행해도 `.gitignore`에 등록된 파일이 목록에 나타나지 않는다. `.gitignore` 파일 자체는 Git이 추적해도 무방하며, 오히려 팀원들과 공유하는 것이 안전하다.

```bash
git add .gitignore
git commit -m "create .gitignore"
```

## 실습 결과

### Git 명령어별 역할 정리

| 명령어 | 역할 |
|---|---|
| git init | 현재 폴더를 로컬 저장소로 초기화 |
| git status | 현재 저장소의 상태(Working Directory/Staging Area) 확인 |
| git add [파일명] | 파일을 Staging Area로 이동 |
| git commit -m "메시지" | Staging Area의 파일을 Repository에 기록 |
| git log | 커밋 이력 확인 |
| git restore . | Working Directory의 변경 사항을 마지막 커밋 상태로 되돌림 |
| git switch --detach [해시] | HEAD를 특정 커밋으로 이동 |
| git switch main | HEAD를 최신 상태(main 브랜치)로 복귀 |

### 커밋 상태 전이 과정

| 단계 | 상태 | 명령어 |
|---|---|---|
| 1 | 파일 생성/수정 | 자동으로 Untracked 또는 Modified 상태 |
| 2 | 커밋 대상 지정 | git add로 Staging Area 상태로 전환 |
| 3 | 커밋 생성 | git commit으로 Repository에 반영 |

실습을 통해 확인한 핵심은, Git의 세 가지 상태(Working Directory·Staging Area·Repository)가 각각 별도의 명령어(수정, git add, git commit)를 거쳐야만 다음 단계로 넘어간다는 점이다. 이 구조 덕분에 작업 중인 여러 파일 가운데 준비된 파일만 골라 커밋할 수 있다.

## 배운 점

**새롭게 이해한 내용**: Git이 파일을 복사해서 버전을 늘리는 방식이 아니라, 항상 최종 상태의 파일 하나만 유지하면서 내부적으로 커밋이라는 기록을 쌓아간다는 원리가 명확해졌다. HEAD라는 포인터 하나로 과거 커밋과 현재 커밋 사이를 오갈 수 있다는 점도, 파일을 여러 버전으로 복사해 관리하던 기존 방식과 비교했을 때 왜 Git이 체계적인지 이해하는 데 도움이 됐다.

**어려웠던 점**: git commit 실행 시 갑자기 전환되는 Vim 텍스트 에디터 화면이 낯설었다. 입력 모드로 전환하는 `i`, 저장 후 종료하는 `:wq` 같은 명령이 익숙하지 않아 여러 차례 반복 연습이 필요했다. 또한 Staging Area와 Repository의 차이, 그리고 왜 이 두 단계를 거쳐야 하는지가 처음에는 번거롭게 느껴졌다.

**해결 과정**: hello.py와 world.py 두 파일을 동시에 다루면서 하나는 커밋하고 하나는 커밋하지 않는 실습을 직접 따라가 보니, Staging Area가 왜 필요한지(여러 파일 중 원하는 파일만 골라 기록하기 위해) 체감할 수 있었다. HEAD 이동 실습에서도 `git switch --detach`로 이전 커밋으로 이동했을 때 실제로 파일이 사라지고, `git switch main`으로 돌아왔을 때 다시 나타나는 과정을 눈으로 확인하니 개념이 명확해졌다.

**앞으로 적용 가능한 부분**: 작업 단위를 작게 나눠 커밋하고 메시지를 구체적으로 작성하는 습관은 앞으로 어떤 프로젝트를 진행하든 코드 이력을 관리하는 기본기가 될 것으로 보인다. 특히 `.gitignore`로 API 키 같은 민감한 정보를 커밋 대상에서 제외하는 절차는, 이후 GitHub에 코드를 올리기 시작하면 반드시 지켜야 하는 보안 습관으로 남을 전망이다.

## 마무리

1일차는 버전 관리라는 개념의 필요성에서 출발해, Git과 GitHub의 차이, Repository·Commit·Branch·HEAD라는 핵심 개념, 그리고 Working Directory·Staging Area·Repository로 이어지는 세 가지 상태를 실습으로 확인했다. git init으로 저장소를 만들고, git add와 git commit으로 변경 이력을 기록하고, git log와 git switch로 커밋 사이를 오가는 기본 흐름을 손으로 직접 익혔다. 마지막으로 다룬 .gitignore는 API 키 같은 민감한 정보를 실수로 커밋하지 않도록 막아주는 필수적인 안전장치였다. 내일은 오늘 다루지 않은 GitHub을 본격적으로 배우며, 로컬에서 작업한 내용을 원격 저장소에 올리고 다른 사람과 협업하는 과정을 실습할 예정이다.
