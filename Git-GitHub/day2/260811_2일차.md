# 브랜치를 나누고 다시 합치는 법: Git과 GitHub 2일차

## 들어가며: 로컬 사용법을 넘어 협업의 기초로

Git과 GitHub 2일차는 1일차에서 배운 기본 명령어(git init·add·commit·log)를 퀴즈로 복습하는 것으로 시작했다. 어제가 혼자서 버전을 기록하는 방법을 다뤘다면, 오늘은 그 기록을 여러 갈래로 나누고 다시 합치는 방법, 즉 브랜치와 병합을 다뤘다. 오후에는 로컬에서만 관리하던 코드를 GitHub이라는 원격 저장소에 올리는 과정까지 이어졌다. 이 시간의 목표는 세 가지다. 첫째, 브랜치를 만들고 전환하고 삭제하는 방법을 익히는 것이다. 둘째, 브랜치를 다시 합치는 두 가지 방식(Fast-forward, 3-way Merge)과 그 차이를 이해하는 것이다. 셋째, 같은 코드를 다르게 수정했을 때 발생하는 충돌(Conflict)을 해결하고, GitHub에 코드를 올리는 것까지 실습하는 것이다.

## 핵심 개념 정리

### 복습: Commit, 브랜치, Staging Area

1일차 내용을 퀴즈로 되짚었다. Git에서 하나의 작업 단위를 기록하는 것은 Commit이며, 버전이라는 일반적인 용어 대신 Git에서는 Commit이라는 용어를 쓴다. Git을 사용하는 가장 기본적인 목적은 코드의 변경 이력을 관리하는 버전 관리이며, 팀원과의 코드 공유나 서버 배포는 이를 활용한 부가적인 기능이다. Working Directory와 Staging Area는 둘 다 로컬에서 일어나는 일이며, 변경 사항이 자동으로 커밋되는 기능은 없다 — 항상 `git add`로 커밋할 파일을 직접 선택해야 한다.

### 브랜치 관리 전략: 목적에 맞게 나누고 이름 짓기

브랜치를 무분별하게 만들고 합치면 코드 상태가 혼란스러워지기 때문에, 실무에서는 팀 단위로 브랜치 관리 규칙을 미리 정한다. 구체적인 전략은 회사나 팀 규모, 작업 복잡도에 따라 달라지지만, 가장 일반적으로 쓰이는 방식은 다음과 같다.

| 브랜치 | 역할 |
|---|---|
| main | 배포 가능한 안정적인 버전만 유지하는 브랜치 |
| dev(develop) | 실제 작업 대부분이 이루어지는 브랜치. 기능 개발 내용이 누적됐다가 검증되면 main으로 보냄 |
| feature/기능명 | 개별 기능을 개발하는 브랜치(예: `feature/signup`, `feature/login`). 완료되면 dev에 합침 |
| hotfix/... | 긴급한 버그 수정을 위한 브랜치 |

여러 명이 dev 브랜치에 동시에 직접 작업하면 코드가 섞일 수 있기 때문에, 기능 단위로 feature 브랜치를 따로 만들어 작업한 뒤 완료되면 dev로 합치는 흐름이 일반적이다. 다만 혼자 개발할 때는 이렇게까지 복잡하게 나눌 필요는 없으며, 이날 실습은 main과 feature 브랜치만으로 진행됐다.

### 브랜치 생성과 전환: 특정 시점의 코드 복제

`git init`을 하는 순간 우리는 항상 main이라는 기본 브랜치 위에서 시작한다. 새로운 브랜치를 만들면 완전히 빈 상태에서 시작하는 것이 아니라, **브랜치를 만드는 시점의 코드가 그대로 복제**된다.

```bash
git branch feature-ui      # feature-ui라는 이름의 브랜치 생성
git branch                 # 브랜치 목록 확인(별표가 현재 위치)
git switch feature-ui      # feature-ui 브랜치로 이동
git status                 # On branch feature-ui로 확인 가능
```

브랜치를 만든 직후에는 main과 새 브랜치의 코드가 완전히 동일하다 — 폴더를 통째로 복사한 뒤 이름만 바꾼 것과 같은 상태이며, 이는 정상이다. 이후 새 브랜치에서 파일을 추가하고 커밋하면, 그 변경 사항은 **해당 브랜치 위에만 존재**한다. `git switch main`으로 돌아가면 방금 추가한 파일이 보이지 않는다 — 다른 브랜치의 작업 내용이 반영되지 않았기 때문이다. `git log --all --graph` 명령으로 여러 브랜치의 커밋 이력을 트리 형태로 한눈에 확인할 수 있다.

### 브랜치 삭제: 롤백 없이 작업을 폐기하는 법

특정 브랜치에서 작업한 내용이 마음에 들지 않을 때는 별도의 롤백 없이 그 브랜치 자체를 지워버리면 된다.

```bash
git switch main        # 삭제하려는 브랜치 위에서는 자기 자신을 지울 수 없음
git branch -d feature-ui
```

브랜치를 삭제하면 그 브랜치에서만 존재하던 커밋은 로그에서 완전히 사라지고 되돌릴 수 없다. 이는 같은 선상에서 이전 커밋으로 돌아가는 롤백과는 다른 개념이다 — 롤백이 시간을 거슬러 올라가는 것이라면, 브랜치 삭제는 애초에 존재하지 않았던 것처럼 그 갈래 자체를 없애는 것이다.

### 병합(Merge): 브랜치를 다시 합치는 두 가지 방식

다른 브랜치에서 작업한 내용을 현재 브랜치로 가져오는 것을 **Merge(병합)**라 한다. Merge는 기본적으로 브랜치 단위로 이뤄지며, 병합하려는 브랜치로 먼저 이동한 뒤 `git merge <가져올 브랜치>`를 실행한다. Merge 방식은 두 브랜치의 관계에 따라 둘로 나뉜다.

| 방식 | 발생 조건 | 동작 |
|---|---|---|
| Fast-forward | 병합 대상 브랜치가 현재 브랜치의 이후 상태이기만 할 때(분기 이후 다른 변경이 없음) | 새 커밋을 만들지 않고, 현재 브랜치의 커밋 포인터만 앞으로 이동 |
| 3-way Merge | 두 브랜치가 각각 독립적으로 진행되어 서로 다른 커밋을 가질 때 | 두 브랜치의 변경 내용을 모두 포함하는 새로운 병합 커밋을 생성 |

```bash
git switch main
git merge feature-ai   # main이 분기 이후 변경되지 않았다면 Fast-forward
```

두 개의 브랜치(left, right)를 각각 만들어 서로 다른 파일을 커밋한 뒤 main에 순서대로 병합하는 실습을 진행했다. 첫 번째 브랜치(left)는 main과 분기 이후 차이가 없어 **Fast-forward**로 병합됐다 — 커밋 포인터만 이동했다. 두 번째 브랜치(right)를 병합할 때는 main이 이미 앞으로 이동한 상태였기 때문에 단순히 포인터를 옮기는 것으로는 두 브랜치의 내용을 모두 담을 수 없었고, **3-way Merge**가 일어나 두 브랜치의 변경 내용을 모두 포함하는 새로운 병합 커밋이 자동으로 생성됐다.

### Merge Conflict: Git이 대신 결정해주지 않는 순간

두 브랜치가 **같은 파일의 같은 부분**을 서로 다르게 수정했을 때는 Git이 어느 쪽이 맞는지 스스로 판단하지 않는다. 임의로 하나를 선택해 덮어써 버리면 사용자가 모르는 사이에 코드가 유실될 수 있기 때문이다. 이런 상황을 **Conflict(충돌)**라 하며, 최종 코드가 어떤 모습이어야 하는지는 병합을 시도하는 사람이 직접 결정해야 한다.

```bash
git merge b
# Auto-merging hello.py
# CONFLICT (content): Merge conflict in hello.py
```

충돌이 발생한 파일을 열면 다음과 같은 표시가 나타난다.

```
<<<<<<< HEAD
Hello A
=======
Hello B
>>>>>>> b
```

`=`를 기준으로 위쪽은 현재 브랜치의 코드, 아래쪽은 병합해오려는 브랜치의 코드다. 둘 중 하나를 선택하거나, 둘을 조합하거나, 아예 새로운 코드로 대체하는 것까지 모두 개발자의 선택이며 정해진 정답은 없다. 충돌을 해결한 뒤에는 일반적인 커밋 절차와 동일하게 마무리한다.

```bash
git add hello.py
git commit -m "merge conflict in hello.py"
```

이 커밋 역시 두 브랜치의 내용을 하나로 합치는 병합 커밋이라는 점에서, 근본적으로는 3-way Merge와 같은 구조다.

### GitHub: 최종 코드가 아닌 작업 이력 전체를 공유하는 이유

구글 드라이브나 이메일로 파일을 공유하면 최종 상태의 코드만 전달된다. 반면 **GitHub**에 코드를 올리면 그동안의 커밋 이력(누가 언제 무엇을 어떻게 바꿨는지) 전체가 함께 공유된다 — 이것이 코드 공유에 파일 전송 대신 GitHub을 쓰는 핵심 이유다.

GitHub에서 새 저장소(Repository)를 만들 때 설정하는 항목은 다음과 같다.

| 항목 | 의미 |
|---|---|
| Visibility(Public/Private) | Public은 누구나 코드를 볼 수 있음, Private은 본인만 볼 수 있음 |
| README | 프로젝트 설명 문서. 자동 생성 여부를 선택 |
| .gitignore | 버전 관리에서 제외할 파일 목록을 자동 생성할지 여부 |
| License | 오픈소스로 공개할 때 다른 사람이 코드를 어느 범위까지 쓸 수 있는지 명시하는 문서 |

이미 로컬에 코드와 `.gitignore`가 준비되어 있는 경우에는 README·gitignore·license를 자동 생성하지 않고 빈 저장소로 만든 뒤, 로컬 코드를 업로드하는 방식을 사용했다. 로컬 저장소의 코드를 원격 저장소로 업로드하는 행위를 **push**라 부른다. push를 하려면 로컬 저장소에게 "어디로 올릴지"를 먼저 알려줘야 하며, 이 과정에서 원격 저장소 주소를 등록하는 절차가 필요하다.

## 실습 과정

### 브랜치 생성·전환·삭제 실습

`feature-ui`, `feature-ai` 브랜치를 각각 만들어 새 파일(`ui.py`, `ai.py`)을 추가·커밋한 뒤, `git switch main`으로 돌아가면 해당 파일이 보이지 않는 것을 확인했다. `git branch -d`로 `feature-ui`를 삭제한 뒤 해당 브랜치로 전환을 시도하면 오류가 발생해, 삭제된 브랜치의 커밋은 되돌릴 수 없다는 점을 실습으로 확인했다.

### Fast-forward Merge 실습

`branch-left`, `branch-right` 두 브랜치를 만들어 각각 `left.py`, `right.py`를 커밋한 뒤, main에서 `git merge left`를 실행했다. main과 left 사이에 분기 이후 다른 변경이 없었기 때문에 Fast-forward로 병합됐고, VS Code에서 main 브랜치임에도 `left.py`가 나타나는 것을 확인했다.

### 3-way Merge 실습

이어서 main에서 `git merge right`를 실행하자, 이번에는 포인터 이동만으로 해결되지 않아 3-way Merge가 발생했다. 커밋 메시지 작성 화면(Vim)이 자동으로 열렸고, 기본 제공된 메시지(`Merge branch right`)를 그대로 사용해 `:wq`로 저장했다. `git log --all --graph`로 확인한 결과, main·left·right 각각의 커밋이 새로운 병합 커밋 하나로 합쳐진 구조가 트리 형태로 나타났다.

### Merge Conflict 실습

기존 브랜치를 모두 정리한 뒤, `branch-a`와 `branch-b`를 새로 만들어 같은 파일(`hello.py`)의 같은 줄을 각각 다르게 수정했다(`Hello A`, `Hello B`). main에 a를 먼저 병합하자 Fast-forward로 처리됐지만, 이어서 b를 병합하려 하자 `Auto-merging hello.py` 이후 `CONFLICT (content): Merge conflict in hello.py`가 발생했다. 충돌 표시(`<<<<<<<`, `=======`, `>>>>>>>`)가 있는 파일을 직접 열어 두 내용을 `Hello A & B`로 합치기로 결정한 뒤, `git add`와 `git commit`으로 충돌 해결을 완료했다.

### GitHub 저장소 생성과 Push

GitHub에서 Public 저장소를 README·gitignore·license 없이 빈 상태로 생성한 뒤, 로컬 저장소를 원격 저장소에 연결하고 push하는 과정을 진행했다. 실습 중 `git push origin main` 시도에서 `remote origin already exists`(이미 원격 저장소가 등록된 상태에서 재등록을 시도) 오류와 `remote: Repository not found`(저장소 주소 오타로 존재하지 않는 경로를 가리킴) 오류가 실제로 발생했고, `git remote -v`로 현재 등록된 원격 저장소 주소를 확인하며 원인을 짚었다. 이 과정에서 `ssh -T git@github.com`으로 GitHub과의 SSH 연결 상태를 점검하는 방법도 함께 다뤄졌다.

## 실습 결과

### Merge 방식 비교

| 상황 | Merge 방식 | 결과 |
|---|---|---|
| main과 분기 이후 변경 없음(left) | Fast-forward | 새 커밋 없이 포인터만 이동 |
| main이 이미 앞서 있고 다른 파일을 각각 수정(right) | 3-way Merge | 두 브랜치 내용을 포함하는 병합 커밋 생성 |
| 같은 파일의 같은 부분을 다르게 수정(a, b) | 3-way Merge + Conflict | 자동 병합 실패, 수동 해결 후 병합 커밋 생성 |

### Push 과정에서 발생한 오류와 원인

| 오류 메시지 | 원인 |
|---|---|
| `remote origin already exists` | 원격 저장소가 이미 등록된 상태에서 다시 등록을 시도함 |
| `remote: Repository not found` | 등록한 저장소 URL에 오타가 있어 존재하지 않는 경로를 가리킴 |

두 브랜치의 코드가 겹치지 않을 때는 Git이 자동으로 병합할 수 있지만, 같은 부분이 충돌할 때는 반드시 사람이 개입해야 한다는 원칙이 실습 전반에서 일관되게 확인됐다. push 과정의 오류들도 마찬가지로, Git이 스스로 문제를 해결해주지 않고 정확한 원인(중복 등록, 오타)을 사용자가 직접 진단해야 한다는 점에서 같은 원칙의 연장선에 있었다.

## 배운 점

**새롭게 이해한 내용**: 브랜치를 만드는 순간 "그 시점의 코드가 그대로 복제된다"는 설명이 명확했다. 브랜치가 완전히 새로운 빈 공간에서 시작하는 것이 아니라, 분기 시점의 스냅샷을 공유한 채 이후부터 독립적으로 진행된다는 점을 이해하니, Fast-forward와 3-way Merge의 차이도 자연스럽게 연결됐다 — 분기 이후 한쪽만 변경됐으면 포인터만 옮기면 되고(Fast-forward), 양쪽 다 변경됐으면 두 갈래를 하나로 합치는 새 커밋이 필요하다(3-way).

**어려웠던 점**: 3-way Merge에서 왜 항상 새로운 커밋이 생성되어야 하는지, 그리고 포인터 이동만으로는 왜 해결이 안 되는지가 처음에는 바로 와닿지 않았다. 두 브랜치 중 어느 하나로 포인터를 옮기면 다른 쪽의 변경 내용이 사라지기 때문이라는 설명을 듣기 전까지는 왜 그렇게 복잡한 방식이 필요한지 의문이었다.

**해결 과정**: 강사가 커밋 번호를 붙여 그림으로 설명한 방식(6번에서 분기된 7번, 8번을 각각 6번으로 되돌리거나 서로에게 옮기는 것이 왜 불가능한지)을 따라가며, 두 갈래의 정보를 모두 보존하려면 그 두 정보를 합친 새로운 지점(9번)을 만드는 수밖에 없다는 논리를 이해할 수 있었다. Merge Conflict 실습에서도 마찬가지로, 충돌 마커 안의 위쪽·아래쪽 코드를 직접 눈으로 비교하며 최종 코드를 스스로 결정해보는 과정이 개념을 체화하는 데 도움이 됐다.

**앞으로 적용 가능한 부분**: main·dev·feature 브랜치를 목적에 맞게 나누는 전략은 이후 팀 프로젝트나 실무에서 코드 관리 규칙을 세울 때 기본 틀로 활용할 수 있다. 또한 push 과정에서 겪은 오류(원격 저장소 중복 등록, URL 오타)는 실제로 자주 마주치는 문제인 만큼, `git remote -v`로 현재 상태를 먼저 확인하는 습관을 들이면 이후 비슷한 상황에서 원인을 빠르게 진단할 수 있을 것으로 보인다.

## 마무리

2일차는 브랜치를 생성·전환·삭제하는 기본기에서 시작해, Fast-forward와 3-way Merge라는 두 가지 병합 방식의 차이를 실습으로 직접 확인했다. 같은 파일을 다르게 수정했을 때 발생하는 Merge Conflict를 해결하는 과정에서는, Git이 최종 판단을 사용자에게 맡긴다는 원칙을 되풀이해서 확인할 수 있었다. 오후에는 로컬에서만 다루던 코드를 GitHub 원격 저장소에 올리는 과정을 실습하며, 파일 공유와 달리 GitHub은 코드의 전체 작업 이력을 함께 공유한다는 점을 이해했다. 다음 시간에는 오늘 마무리하지 못한 push 이후의 GitHub 활용법과 협업 워크플로우를 이어서 다룰 예정이다.
