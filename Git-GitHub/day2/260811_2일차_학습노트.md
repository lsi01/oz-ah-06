# Git과 GitHub — 2일차 학습노트

---

## 1. Branch

### 1-1. Branch란

Branch는 기존 작업과 분리된 독립적인 작업 흐름이다. `git init`을 실행하는 순간 항상 `main`이라는 하나의 브랜치 위에서 시작하며, 새로운 브랜치를 만들면 완전히 빈 상태에서 시작하는 것이 아니라 **브랜치를 만드는 시점의 코드가 그대로 복제**된다 — 폴더를 통째로 복사한 뒤 이름만 바꾼 것과 같은 상태다. 이후 각 브랜치에서 파일을 추가·수정하고 커밋하면, 그 변경 사항은 해당 브랜치 위에만 존재하며 다른 브랜치로 전환하면 보이지 않는다.

### 1-2. 브랜치 관리 전략

브랜치를 무분별하게 만들고 합치면 코드 상태가 혼란스러워지므로, 실무에서는 팀 단위로 브랜치 관리 규칙을 미리 정한다. 구체적인 전략은 회사·팀 규모·작업 복잡도에 따라 다르지만, 가장 일반적으로 쓰이는 방식은 다음과 같다.

| 브랜치 | 역할 |
|---|---|
| main | 배포 가능한 안정적인 버전만 유지하는 브랜치 |
| dev(develop) | 실제 작업 대부분이 이루어지는 브랜치. 기능 개발 내용이 누적됐다가 검증되면 main으로 보냄 |
| feature/기능명 | 개별 기능을 개발하는 브랜치(예: `feature/signup`, `feature/login`). 완료되면 dev에 합침 |
| hotfix/... | 긴급한 버그 수정을 위한 브랜치 |

> release 브랜치는 이 강의에서 명시적으로 다루지 않았다. main·dev·feature·hotfix와 함께 널리 쓰이는 Git Flow 전략의 구성 요소라 별도로 보충 학습이 필요하다.

여러 명이 dev 브랜치에 동시에 직접 작업하면 코드가 섞일 수 있어, 기능 단위로 feature 브랜치를 따로 만들어 작업한 뒤 완료되면 dev로 합치는 흐름이 일반적이다. 혼자 개발할 때는 이렇게까지 나눌 필요는 없으며, 이날 실습은 main과 feature 브랜치만으로 진행됐다.

### 1-3. 브랜치 생성·전환·삭제

```bash
git branch feature-ui      # feature-ui 브랜치 생성
git branch                 # 브랜치 목록 확인(별표가 현재 위치)
git switch feature-ui      # feature-ui 브랜치로 이동
git status                 # On branch feature-ui로 확인
```

브랜치를 만든 직후 `git status`로 확인해도 현재 위치는 여전히 원래 브랜치에 있을 수 있다 — 브랜치 생성과 전환은 별개의 명령이다. `git log --all --graph`로 모든 브랜치의 커밋 이력을 트리 형태로 한 번에 확인할 수 있다.

브랜치를 삭제할 때는 그 브랜치 위에서 자기 자신을 지울 수 없으므로 다른 브랜치(main 등)로 이동한 뒤 삭제한다.

```bash
git switch main
git branch -d feature-ui   # 브랜치 삭제
```

삭제된 브랜치에서만 존재하던 커밋은 로그에서 완전히 사라지며 되돌릴 수 없다. 이는 이전 커밋으로 돌아가는 롤백과는 다른 개념이다 — 롤백이 같은 선상에서 시간을 거슬러 올라가는 것이라면, 브랜치 삭제는 그 갈래 자체가 애초에 존재하지 않았던 것처럼 없애는 것이다.

## 2. Merge

다른 브랜치에서 작업한 내용을 현재 브랜치로 가져오는 것을 **Merge(병합)**라 한다. 병합하려는 대상 브랜치로 먼저 이동한 뒤 `git merge <가져올 브랜치>`를 실행하며, 병합 방식은 두 브랜치의 관계에 따라 둘로 나뉜다.

| 방식 | 발생 조건 | 동작 |
|---|---|---|
| Fast-forward | 병합 대상 브랜치가 현재 브랜치의 분기 이후 상태이기만 할 때(그 사이 현재 브랜치에 다른 변경이 없음) | 새 커밋을 만들지 않고, 현재 브랜치의 커밋 포인터를 그대로 이동 |
| 3-way Merge | 두 브랜치가 각각 독립적으로 진행되어 서로 다른 커밋을 가질 때 | 두 브랜치의 변경 내용을 모두 포함하는 새로운 병합 커밋을 생성 |

### 2-1. Fast-forward 실습

`branch-left`, `branch-right` 두 브랜치를 만들어 각각 `left.py`, `right.py`를 커밋했다. main에서 `git merge left`를 실행하자, main과 left 사이에 분기 이후 다른 변경이 없어 Fast-forward로 병합됐다 — 커밋 포인터만 이동했다.

```bash
git switch main
git merge left    # Fast-forward
```

### 2-2. 3-way Merge 실습

이어서 `git merge right`를 실행하자, 이번에는 main이 이미 앞으로 이동한 상태였기 때문에 포인터 이동만으로는 두 브랜치의 내용을 모두 담을 수 없었고 3-way Merge가 일어났다. 커밋 메시지 작성 화면(Vim)이 자동으로 열렸고, 기본 제공된 메시지(`Merge branch 'right'`)를 그대로 사용해 `:wq`로 저장했다. `git log --all --graph`로 확인한 결과, main·left·right 각각의 커밋이 새로운 병합 커밋 하나로 합쳐진 구조가 트리 형태로 나타났다.

### 2-3. Merge Conflict 실습

같은 파일의 같은 부분을 서로 다르게 수정했을 때는 Git이 어느 쪽이 맞는지 스스로 판단하지 않는다. 임의로 하나를 선택해 덮어써 버리면 사용자가 모르는 사이 코드가 유실될 수 있기 때문이다 — 최종 코드가 어떤 모습이어야 하는지는 병합을 시도하는 사람이 직접 결정해야 한다.

`branch-a`, `branch-b`를 만들어 같은 파일(`hello.py`)의 같은 줄을 각각 다르게 수정했다(`Hello A`, `Hello B`). main에 a를 먼저 병합하자 Fast-forward로 처리됐지만, 이어서 b를 병합하려 하자 다음과 같은 충돌이 발생했다.

```
git merge b
# Auto-merging hello.py
# CONFLICT (content): Merge conflict in hello.py
```

충돌 파일을 열면 다음 표시가 나타난다.

```
<<<<<<< HEAD
Hello A
=======
Hello B
>>>>>>> b
```

`=`를 기준으로 위쪽은 현재 브랜치의 코드, 아래쪽은 병합해오려는 브랜치의 코드다. 둘 중 하나를 선택하거나, 둘을 조합하거나, 아예 새로운 코드로 대체하는 것 모두 개발자의 선택이며 정해진 정답은 없다(실습에서는 `Hello A & B`로 합치기로 결정). 충돌을 해결한 뒤에는 일반적인 커밋 절차와 동일하게 마무리한다.

```bash
git add hello.py
git commit -m "merge conflict in hello.py"
```

이 커밋 역시 두 브랜치의 내용을 하나로 합치는 병합 커밋이라는 점에서, 근본적으로는 3-way Merge와 같은 구조다.

## 3. GitHub: 원격 저장소 생성과 Push

### 3-1. 왜 파일 공유 대신 GitHub인가

구글 드라이브나 이메일로 파일을 공유하면 최종 상태의 코드만 전달된다. GitHub에 코드를 올리면 그동안의 커밋 이력(누가 언제 무엇을 어떻게 바꿨는지) 전체가 함께 공유되어, 받는 사람이 과거 시점으로 롤백하거나 예전 작업 내용을 확인할 수 있다.

### 3-2. 저장소(Repository) 생성

GitHub에서 새 저장소를 만들 때 설정하는 항목은 다음과 같다.

| 항목 | 의미 |
|---|---|
| Visibility(Public/Private) | Public은 누구나 코드를 볼 수 있음, Private은 본인만 볼 수 있음 |
| README | 프로젝트 설명 문서. 저장소 생성과 동시에 자동 생성할지 여부를 선택 |
| .gitignore | 버전 관리에서 제외할 파일 목록을 자동 생성할지 여부 |
| License | 오픈소스로 공개할 때 다른 사람이 코드를 어느 범위까지 쓸 수 있는지 명시하는 문서 |

이미 로컬에 코드와 `.gitignore`가 준비되어 있는 경우, README·gitignore·license를 자동 생성하면 저장소가 비어 있지 않은 상태로 시작되어 이후 업로드 시 충돌이 발생할 수 있다. 그래서 세 옵션을 모두 끄고 완전히 빈 저장소로 만든 뒤, 로컬 코드를 업로드하는 방식을 사용했다.

### 3-3. Push

로컬 저장소의 코드를 원격 저장소로 업로드하는 행위를 **push**라 한다. push를 하려면 로컬 저장소에게 "어디로 올릴지"를 먼저 알려줘야 하며, 이 과정에서 원격 저장소 주소를 등록하는 절차(`git remote add origin <저장소 주소>`)가 필요하다.

실습 중 `git push origin main` 시도에서 다음 오류가 실제로 발생했다.

| 오류 메시지 | 원인 |
|---|---|
| `remote origin already exists` | 원격 저장소가 이미 등록된 상태에서 다시 등록을 시도함 |
| `remote: Repository not found` | 등록한 저장소 URL에 오타가 있어 존재하지 않는 경로를 가리킴 |

두 오류 모두 `git remote -v`로 현재 등록된 원격 저장소 주소를 먼저 확인해 원인을 진단한다. 추가로 `ssh -T git@github.com`으로 GitHub과의 SSH 연결 상태를 점검하는 방법도 함께 다뤄졌다.

## 핵심 정리

- 브랜치는 분기 시점의 코드를 복제해 독립적으로 진행하는 작업 흐름이며, 삭제해도 원본(main)에는 영향을 주지 않는다.
- 실무에서는 main·dev·feature·hotfix로 브랜치 역할을 나누되, 구체적인 규칙은 팀마다 다르다.
- 병합은 분기 이후 한쪽만 변경됐으면 Fast-forward(포인터 이동), 양쪽 다 변경됐으면 3-way Merge(병합 커밋 생성)로 이뤄진다.
- 같은 파일의 같은 부분이 충돌하면 Git은 자동으로 결정하지 않으며, 충돌 마커를 직접 편집해 해결한 뒤 add·commit으로 마무리해야 한다.
- GitHub은 최종 코드가 아니라 커밋 이력 전체를 공유하는 데 목적이 있으며, push 전에는 반드시 원격 저장소 주소를 등록해야 한다.
